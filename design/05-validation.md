## 2. 核验项 1：三来源导入的可行性与关键限制（初步 → 最终结论）

| 来源 | 接入方式 | 可行性结论 | 关键限制（必须写入设计约束） | 证据 |
|------|----------|------------|------------------------------|------|
| **Notion** | 官方"导出为 Markdown & CSV"（一次性）+ 可选 API `/v1/blocks/{id}/children` | **可行（只读导入优先）** | ① 官方导出是**快照**，非增量；② 社区 MCP 的 markdown 转换属**实验性**，**写入/编辑会丢结构** → 首版只做**只读导入**，不做双向写回；③ 数据库型页面导出为 CSV，与正文分离，需二次拼装 | `00-precheck-notes.md`；本轮复核一致 `[A]`/`[E]`(官方导出存在) |
| **Logseq** | 本地 `logseq-mcp`（本地 API + token，含 search/create/update page） | **可行**，可选"导入"或"直连" | ① 需 Logseq 桌面端运行 + API 开启 + token；② **其 create/update/delete 工具若被 AI 直调，会绕过我们的确认闸** → 必须纳入同一写入边界（见 §5.3）；③ 需确认双链/标签在读取侧的还原度（`[Q]`） | `00-precheck-notes.md` `[A]` |
| **为知笔记** | **无官方 MCP → 必须自建独立适配层** | **可行但最高风险** | ① 会员导出限制；② 导出多为 HTML，**样式残留**；③ 图片走 `wiz://` 私有协议，需重写链接；④ 加密笔记需先解密；⑤ 协作笔记走 WebSocket，导出可能不完整 | `00-precheck-notes.md` `[A]` |

**升级后的最终结论**：
1. 三来源**均无"不可逾越"的障碍**，但**保真度差异极大**：Logseq（原生 md）> Notion（官方导出 md/csv）> 为知（自建适配 + HTML 清洗）。→ 首版按 T2 M6 做 **≥1 条通路**，建议 **Logseq 优先、Notion 次之、为知最后**。
2. **为知必须配"人工可介入的降级路径"**（lead 已裁定）：格式探测失败时按 T3 **E-12** 标记"该来源待验证"，**不阻塞其它来源**，并给出"换导出方式/手工补"出口。
3. **新增设计约束（本轮提出）**：logseq-mcp 的写工具与导入 MCP 的写工具，**都必须走与知识 MCP 相同的确认闸**——否则"100% 写入可确认"会被旁路。

## 3. 核验项 2：召回强于关键字的机制可行性（初步 → 最终结论）

- **机制层：可行 `[A]`**。本地可用 **SQLite FTS5（BM25）** + **本地嵌入（如 Ollama）向量检索**，两路结果可用 **RRF 融合**，需要时再加轻量 rerank。这不需要联网、不需要托管服务，符合"本地可控"前提。
- **"强于关键字"的可判定性：仍不可测 `[Q]`**。T1 §7.7 已指出：S3 只是诉求，缺可测标准。当前**没有任何本项目的数据**能证明"混合召回 > 关键字召回"。
- **必须做的三件事（否则不可验证）**：
  1. 建 **20–30 条评测集**（真实问句 + 人工标注的相关条目）；
  2. 定指标（对齐 T2 §6.1）：Top-1 ≥ 70% / Top-5 ≥ 90% `[A]`，并**同时测一次纯关键字基线**做对照；
  3. 定义"无结果"的判定口径 —— 必须如 T3 **E-01** 一样**如实说"未找到"，不得编造**。
- **已知效果上限**：召回质量强依赖**本地嵌入模型**，弱模型会拖累语义路；这是选型风险，不是设计缺陷。

> 裁决：把"召回强于关键字"表述为**目标 + 待评测**，**不得**在设计方案中写成"已实现更强召回"。

## 4. 核验项 3：密钥隔离与快速反填（初步 → 最终结论）

### 4.1 隔离（知识库零明文）——**机制可行 `[A]`**
- 可行做法：外部工具（1Password CLI `op read` / `op://` / `op run`；Bitwarden CLI）持有真实 secret；知识库只存**账号引用**（账号名 + 用途 + 位置 + `vault:` 指针），与 T3 §4.3、T2 §6.2 一致。
- **本轮新增：零明文必须在三个环节同时成立**，缺一即破功：
  1. **导入解析前**：历史笔记里很可能**本来就写着密码**（T1 A5）。若直接解析→嵌入，明文会进入向量索引 → **导入管线必须先做 secret 扫描/脱敏**（对齐 T4 §3.4 的拦截与 T3 E-15）。
  2. **索引层**：向量库/全文索引**不得入库明文 secret**，检索结果也不得返回明文片段。
  3. **渲染层**：UI/日志/会话记录**永不出现明文**（T3 P4、T4 密钥四态 P3 = 永不呈现）。
- **可核验判据**：`知识库文件 + 索引 + 日志 + 导出物` 中明文 secret 命中数 = **0**（T2 §6.2）。

### 4.2 快速反填（autofill）——**端到端未验证 `[Q]`**
- "只存指针 + 运行时取用 + 脱敏"这条链在 CLI 层可支撑 `[A]`；但用户要的"**快速反填到实际使用位置**"取决于落点：
  - 浏览器表单 → 需要浏览器扩展/连接器，**未验证**；
  - 终端/CLI → 可用 `op run` 注入环境变量，较易；
  - 桌面 App → 需辅助功能 API，**未验证**。
- **关键安全点**：反填**不得经过 AI 上下文**（T3 §8）。这意味着连接器应由**用户动作直接触发**，且**只返回"已填充/失败"**，不把明文回给模型。此机制**设计上成立、行为未实测**。
- **裁决（与 lead 一致）**：本方案只表述为"**指针化 + 运行时取用 + 脱敏**"，**不得**写成"已实现一键反填到任意表单"。T2 §6 已把 N9（一键反填任意表单）列为**不做**，一致。

### 5.3 ⚠ 重要缺口："100% 写入可确认"不能只靠提示词

**问题**：MCP 只暴露"工具"。如果知识 MCP 暴露了**无条件的 `add`/`update`**，AI 客户端（Cursor/Claude 等）可以直接调用它，**跳过** T3 设计的确认面板——"100% 经确认"就不再成立。这不是 UI 问题，是**协议层问题**。

**建议机制（动工前定稿）**：知识 MCP **不暴露直接写**，改为**两阶段协议**：
1. `propose_write(...)` → 返回 `proposal_id` + diff（**不落盘**）；
2. `commit_write(proposal_id, confirmation_token)` → 仅当 token 由**用户确认动作**（客户端确认面板/CLI）签发时才执行写入；
3. AI 侧**拿不到** `confirmation_token`，因此无法自行提交；
4. 若宿主客户端提供**工具调用审批钩子**，可作为第二道保险，但**不单独依赖**它。

**等级**：`[A]` 机制可行 + `[Q]` 待实测。**在真机验证前，设计方案中"100% 写入可确认"应表述为"设计目标 + 已定强制机制"，而非"已实现"。**
**同类风险**：`logseq-mcp` 等的写工具同样要纳入该协议（§2 结论 3）。

## 7. 原型与模拟范围（明确"做了什么/没做什么"）

### 7.1 原型
- 文件：`<TEAM_WORKSPACE>`
- 形态：**单文件静态 HTML**（零依赖、零网络），可直接双击用浏览器打开。
- 目的：**只验证 T4 §1.5 的"边色 + 徽标"状态语言**与 T3 关键流程的状态切换（T4 明确点名的优先验证项），并为 E-01/02/07/08/12/15 提供可点状态。

### 7.2 模拟了什么
- 卡片**状态机**：待确认 → 已确认·可撤销 → 已撤销；拒绝；疑似密钥**阻断**（确认按钮禁用）；无结果态；低置信态；
- **密钥脱敏**呈现（P1 零字符 / P2 掩码 + 5s 倒计时复原）、反填**成功/失败**两种结果文案（失败态不回显任何 secret 片段）；
- **导入向导**：三项保真度指标 + 丢失清单 + 为知"待验证"降级提示；
- 顶部**三项状态可见性**（召回可用 / 密钥已连 / 索引就绪）。

### 7.3 没模拟什么（**不得当作产品能力**）
- ❌ 真实知识 MCP / 真实混合检索与排序质量；❌ 真实密码管理器取用与浏览器扩展反填；❌ 真实导入解析（无真实 Notion/Logseq/为知数据）；❌ 性能、时延、并发；❌ 多助手适配、多用户、i18n；❌ 后端持久化与审计存储。
- 原型中所有条目、路径、指标数字均为**硬编码演示数据**。

## 9. 后续验证清单（可执行步骤）

> 建议按序执行；每项给出"可判定通过标准"，避免再次落入"看起来可行"。

**A. 写入确认强制机制（对应 R1，最高优先）**
1. 起草知识 MCP 接口：只暴露 `propose_write` / `commit_write`（**不暴露裸 add/update**）。
2. 写一个最小 MCP server + 一个测试客户端，尝试**绕过**确认直接提交 → **通过标准：无 token 时 `commit_write` 必须被拒**。
3. 在目标宿主（Cursor/Claude 等）实测：AI 能否不经用户动作写入 → **通过标准：不能**。
4. 复核 logseq-mcp 等第三方写工具是否被纳入同一闸门。

**B. 召回评测基线（对应 R2）**
1. 建 20–30 条评测集（问句 + 人工标注相关条目，覆盖"换述/模糊记忆/同义词"）。
2. 分别跑：纯 FTS5(BM25) 基线 vs **FTS5+向量(RRF)**。
3. **通过标准**：混合 Top-1 ≥ 70%、Top-5 ≥ 90% 且**不低于**基线；无结果用例 100% 如实"未找到"。

**C. 密钥零明文（对应 R5/R6/R3 相关）**
1. 用 T4 §3.4 的反例构造一份"含明文密码"的笔记，跑导入管线。
2. 扫描**知识库文件 / 索引 / 日志 / 导出物** → **通过标准：明文命中数 = 0**。
3. 反填：在浏览器与 CLI 两个落点各做一次，验证**明文不经 AI 上下文**、界面**不回显**。

**D. 导入保真度（对应 R5/R7）**
1. 各来源取一份**真实**小样本（Logseq 库 / Notion 导出 / 为知导出）。
2. 产出三项指标 + 丢失清单 → **通过标准**：与 T2 §6.5 口径一致，丢失项**逐条可列**、不静默丢弃。
3. 为知：至少验证一种导出格式能否解析；不能则该来源走 E-12 降级。

**E. 原型体验实测（对应 R3，可由设计侧低成本补齐）**
1. 在装有 Chrome 的机器上打开 `05-prototype.html`，跑桌面(1280×800)与窄屏(390×844)。
2. 逐条点按 E-01/02/07/08/12/15 六个状态，确认可被理解。**通过标准**：受试者仅凭"边色+徽标"能正确回答"这条写进去了没有"（T4 §1.5 的核心假设）。
3. 检查对比度（≥4.5:1）、键盘可达、`prefers-reduced-motion`。

**F. 设计稿收口（对应 §6）**
1. T4 补 3 个态：低置信候选 / 撤销已过期 / 三项状态点规格；统一"账号引用"术语。
2. T6 汇总时回灌 `00-precheck-notes.md` 并删除 T2 §7 的过期注记。
