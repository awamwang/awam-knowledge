## 0. 术语表（全文统一口径）

> 本表解决分册间的**命名不一致**问题。凡后文出现的术语，一律以本表为准。

| 术语 | 定义 | 说明 |
|------|------|------|
| **对话式知识层** | 本系统的产品定位：以 AI 会话为唯一主入口的本地知识访问层 | 替代 Notion/Logseq/为知的界面化操作 |
| **本地真相源** | 承载知识的**本地 Markdown 文件夹**（可迁移、可被外部编辑） | 索引可重建，索引不是真相源 |
| **知识 MCP** | 访问本地真相源的 MCP 服务，暴露 `search` / `propose_write` / `commit_write` 等接口 | 是访问层，不是唯一存储 |
| **密钥连接器** | 对接 **Bitwarden**（v1.1 决策锁定的密码管理器）的连接器或 CLI，负责凭据的运行时取用 | 与知识域**物理隔离**；1Password 仅列备选、**不作目标** |
| **账号引用（Account Ref）** | 知识库内的条目，只记"哪有账号、用在哪、怎么用"的**指针**（如 `{{secret:vault:github/pat#1}}`） | **全文统一用"账号引用"**；旧称"凭据引用"作废 |
| **凭据（Credential / Secret Entry）** | 存放于**外部密码管理器内的 secret 本体** | 与"账号引用"严格区分，避免混淆 |
| **反填浮层（V3）** | 触发凭据取用/填充的界面层（**agent 取用路径**下的引用/触发视图） | 视图名沿用 V3 |
| **读放开 · 写收紧** | 召回（读）顺滑无需确认；任何写入（增/改/删）必须经用户显式确认 | 核心交互原则 |
| **确认闸门（Confirm Gate）** | 拦截写入的唯一闸门，位于**知识 MCP 写接口之前** | 唯一拦截点，见 §7.4 |
| **提案（Proposal）≠ 动作（Action）** | AI 的写入意图只是"提案"，未获用户确认前不产生任何落盘 | 确认闸的语义基础 |
| **指针化 + 运行时取用 + 脱敏** | 反填机制的唯一合规表述：知识库只存指针、需要时才取用、全程脱敏；**主用途 = 供 AI agents 运行时取用凭据引用**（v1.2） | **禁止**表述为"一键反填到任意表单已实现" |
| **保真度三项** | 导入质量指标：**条目数一致率 / 标签·双链保留率 / 附件可用率**；**v1.3：附件可用率细化为"结构化可解析率"，且必须先过"解析器自检"否则数字不可信** | 配套"丢失清单" |
| **结构化可解析率** | 导入保真度的可测口径 = Markdown→附件**相对引用可解析率**（v1.3，T21 `[实测]` 真实 graph 428 md/204 附件 = **100%**） | **前置条件 = 解析器自检通过** |
| **解析器自检（强制机制）** | 导入器的链接解析须先过合成夹具自检（括号深度 / 内嵌双链 `[x]([[页面]])` / 引号包裹 URL）；v1.3 列为**强制机制** | 朴素正则曾**大规模伪报缺失**（可解析率 44.7%→修正 100%），见 §3.4 |
| **丢失清单（一等产物）** | 导入中无法保留 / 未被引用、必须**逐条列出**的项；**v1.3 升级为一等产物**，就地纳入导入 job 的 `errors[]` | 严禁静默丢弃（对齐 E-11/E-12） |
| **密钥四态 P0–P3** | 凭据的呈现态：P0 不存在 / P1 存在但不可见（默认）/ P2 掩码可见（受限）/ P3 完整明文（本系统 UI 永不呈现） | 见 §5.3 |
| **状态语言（边色 + 徽标）** | 系统卡用左竖条语义色 + 文字徽标表达状态的统一语言 | 见 §7.3 |
| **召回 hybrid** | BM25（精确词）+ 向量（语义）混合检索，可加 RRF 融合 / Rerank；**v1.4：BM25-only 基线已建（recall@1 0.6154 / @5 0.8462 / MRR 0.7003）；M2 向量 hybrid 已 `[实测]`（T27）但未强于 BM25-only——仅救回跨语言盲区**；**v1.5（T31/T33/T34）：经加权 RRF·并集·表面路由·标题×4 及其叠加多轮对照，均未使 hybrid 强于词法基准，唯一模型无关净增益 = 标题×4（词法侧）** | 见 §4.2 |
| **优先级口径** | **P0** = 阻塞性或核心必备；**P1** = 影响体验、可后置；P2 = 可延后 | 全文统一 |

### 1.2 产品定位与价值主张

> **一句话**：用一个本地可控、可自接 MCP 的**"对话式知识层"**，替代需要人工维护界面的 Notion / Logseq / 为知笔记——知识以**本地文件为唯一真相源**，召回用**语义混合检索（强于关键字）**，密钥与知识**物理隔离（只存指针、运行时取用）**，任何写入都要你点头。 `[E]`（源文档"需求"+"用户选择"）· `[选型依据]` 源文档"回答 2 · 本地栈建议"

**定位三支柱**：

| 支柱 | 含义 | 依据 |
|------|------|------|
| **对话优先、弱化界面** | 检索与录入主入口是 AI 会话；界面只保留"确认/查看/撤销"写入门与状态可见性 | `[E]` 诉求①⑤ |
| **本地可控、自接 MCP** | 数据落本地文件/库；MCP 是访问层；一套栈可挂 Cursor/Claude 等多助手 | `[E]` S8；JTBD-6 |
| **知识与密钥物理隔离** | 知识库只存账号引用，绝不存明文；凭据由 **Bitwarden** 持有 | `[E]` S4/S9；JTBD-3；v1.1 决策锁定 Bitwarden |

**我们是什么 / 不是什么**：

| 我们是 | 我们不是 |
|--------|----------|
| 本地优先的**个人**知识层（P0：技术型、单人自用）`[A]` | 面向大众的 SaaS / 云同步托管的封闭产品 `[Q]` |
| 对话式召回 + 会话式录入的**访问层** | Notion 式目录/排版/看板**管理界面** |
| MCP 生态里的**一组 skill/连接器**（知识 MCP + 密码管理器连接器） | 单一万能 Agent / 自研密码管理器 |
| 以 Markdown 为唯一真相源的**可迁移**方案 | 封闭第二大脑、数据锁定的黑盒 |

`[选型依据]` "本质是 记忆/RAG MCP + 密码管理器连接器 两个 skill 拼起来，而不是单一万能 Agent" —— 源文档"技能形态"。

### 1.3 目标用户（P0）

- **P0 · 核心用户**：`[E]` 本地优先的**技术型知识工作者**（即需求发起人）。能理解 MCP、向量检索、密码管理器，愿意自己搭栈；已用 Notion/Logseq/为知并对"界面化维护"疲劳；`[A]` 同时使用多个 AI 助手（Cursor/Claude），对数据主权敏感。
  - **设计含义**：可接受命令行/配置文件/一次性搭建成本；**不能接受**为日常使用反复手动维护知识库结构。
- **P1 · 相邻用户**（次要兼容目标，非设计中心）：`[A]` 同类但技术能力略低的"本地优先 + 多助手"进阶用户。`[Q]` 是否存在、规模多大待调研。
- **明确非目标**：`[Q]` 纯非技术用户（不会配置 MCP）；`[Q]` 团队协作/多人共享知识库。
- `[A]` **结论**：首版为**单用户、本地、技术型**场景；任何"多人/云端/免配置"设计视为超出范围。

## 2. 总体架构

### 2.1 六层能力域总览

**主轴**：`本地文件（真相源） → 知识 MCP（读/写接口） → AI 助手（会话）`；**密钥侧**独立为 `密码管理器 → 密钥连接器`，与知识层**零明文耦合**。

```
        ┌────────────────── AI 会话与写入边界层（L5） ──────────────────┐
        │  对话召回（读，放开）        会话录入（写，需确认闸门）        │
        └───────────▲───────────────────────────────────▲────────────┘
                    │ MCP: search                          │ MCP: propose/commit (确认后)
        ┌───────────┴───────────────────────────────────┴────────────┐
        │           存储与召回层（L2）：Markdown 真相源 + 向量/BM25 索引 │
        └───────────▲─────────────────────────────────────────────────┘
                    │ 切块/嵌入/写入
        ┌───────────┴───────────┐        ┌───────────────────────────┐
        │      导入层（L1）      │        │   安全与密钥层（L3）       │
        │ Notion / Logseq / 为知 │        │ Bitwarden（决策锁定）      │
        └───────────────────────┘        └───────────▲───────────────┘
                                                     │ 指针/引用 + 运行时取用
                                         ┌───────────┴───────────────┐
                                         │        反填层（L4）         │
                                         │ 指针化 · 运行时取用 · 脱敏  │
                                         └───────────────────────────┘
        ┌──────────────── 横切：配置与适配层（L6）· MCP 接线 ─────────────┐
        └──────────────────────────────────────────────────────────────┘
```

| 层 | 职责 | 关键约束 | 优先级 |
|----|------|----------|--------|
| **L1 导入层** | 把三来源历史知识一次性搬入本地真相源 | 本地执行、只读原库；**按来源分通路**，不强求统一管道 | P0（分批） |
| **L2 存储与召回层** | 持有真相源；提供切块+嵌入索引与 hybrid 召回 | 真相源必须是本地文件；索引可重建 | **P0（心脏）** |
| **L3 安全与密钥层** | 管理账号/凭据，"指针注册 + 运行时取用" | 知识库/索引/日志/导出物**零明文**；不自研密钥库 | **P0（基石）** |
| **L4 反填层** | 按指针运行时取用并填充到目标位置，全程脱敏 | 用户主动触发；明文不落知识库/日志/AI 上下文 | P1 |
| **L5 会话与写入边界层** | 对话式召回（读）+ 会话式录入（写）+ 确认闸门 | **读放开、写收紧**；未找到不得编造 | **P0** |
| **L6 横切·配置与适配层** | 让知识 MCP 与密钥连接器被多助手复用；管理本地配置 | 配置本地化、可迁移；**配置不落 secret 明文** | P1 |

`[选型依据]` "Cursor/Claude/助手侧都能挂同一套" —— 源文档；`[选型依据]` hybrid 召回来自源文档"召回"段。

### 2.2 数据流

- **读路径（放开）**：AI 会话 → 知识 MCP `search` → L2 hybrid 召回 → 结果卡（带来源路径+行号+相关度）。**不经任何确认**。
- **写路径（收紧）**：AI 会话 → 知识 MCP `propose_write`（返回 `proposal_id`+diff，**不落盘**）→ 用户确认 → `commit_write(proposal_id, confirmation_token)` → 落盘 + 审计 + 可撤销。
- **密钥路径（隔离）**：知识库只存**账号引用**；用户触发反填 → 密钥连接器经密码管理器取用并**直接写入目标字段**，**明文不经 AI 上下文、不进日志**。

### 2.3 知识域与密钥域的物理隔离

- 知识域（L1/L2/L5）与密钥域（L3/L4）**不共享存储、不共享索引**。
- 两者唯一连接是**知识库中的账号引用条目**（指针），它不含任何 secret 字符。
- 因此：**知识库泄密 ≠ 凭据泄密**（JTBD-3 的直接目标）。

### 3.4 保真度与丢失清单（导入质量口径）

- **保真度三项**（实现前必须定义并实测）：**条目数一致率 / 标签·双链保留率 / 附件可用率**。 `[A]`
- **v1.3 收紧（T21）**：附件可用率细化为可测的 **结构化可解析率** —— Markdown→附件**相对引用可解析率**；**前置条件 = 解析器自检通过**（否则数字不成立）。 `[实测]` 真实 Logseq graph：**428 md / 204 附件 / 131 条相对引用全部解析 / 相对引用可解析率 100% / 丢失清单为空 / 遍历错误 0**（`11-import-with-attachments-report.md`；限"最小实现 + 只读导入"范围，**不得外推生产就绪**）。
- **导入能力口径（v1.3，T21）**：为知**跳过**后，导入层对外承诺的通用能力 = **"带附件 Markdown 目录"导入**（Markdown 摄取 + 附件识别/登记含 SHA256 + 相对链接解析 + 缺失检测 + 统计与丢失清单）；附件体积现实（本 graph ≈ **100 MB / 204 个**，其中 **73 个孤儿**）→ 支持"**只索引、按需取用**"，**不强制全量复制**。
- **解析器鲁棒性 + 自检 = 强制机制（v1.3）**：路径含**成对圆括号**、`[别名]([[页面]])` **内嵌双链**、**引号包裹 URL** 是本语料常态 → **任何基于朴素正则的导入器都会严重失真**（实测伪报：可解析率 **44.7% → 修正后 100%**）；故"链接解析"须列入**需自检/回归**的组件，导入器**先过合成夹具自检**（T21 自检 **16/16**）方可对外报保真度数字。
- **丢失清单 = 一等产物（v1.3）**：无法保留 / 未被引用、必须**逐条列出、可见**的项，**严禁静默丢弃**；就地纳入导入 **job 状态机的 `errors[]`**（对齐 E-11/E-12、§10.4）。"未搬过来的资源 / 从未被引用的孤儿附件"比"搬了多少"更影响可用性，须可查。
- 三项指标**必须在"确认落库"前可见**（见 §3.5 导入向导）。

### 3.5 导入流程（F1）与异常出口

1. 选择来源 → 2. 预览与保真度（三项指标 + 丢失清单 + 条目预览）→ 3. **确认落库**（写收紧的最后一步）。
- **E-11 导入部分失败**：成功入库、失败**逐条列出**（不整批回滚、不静默），**丢失清单一等产物就地入 job `errors[]`**（v1.3）。
- **E-12 导入源解析失败**（含为知导出物的清洗/附件修复失败）：标记"该来源待验证"、**不阻塞其它来源**、给降级出口。
- **原库只读**：导入不改动原工具数据（在向导中显式告知）。

### 3.6 导入向导的界面要点（对齐 §7.3 状态语言）

## 4. 存储与召回层（诉求①③）

### 4.1 真相源与索引

- **真相源**：`Markdown/纯文件夹`（首选，可迁移、可被外部编辑）。`[Q]`(Q10) 是否偏向本地向量库待定。
- **索引**：自建 SQLite/LanceDB + hybrid，或复用现有本地知识 MCP。`[选型依据]` 源文档"回答 2 · 知识层/召回"。
- **可重建性**：索引可由真相源重建，**删除索引不丢知识**（对齐 §附录 A §4）。
- 图谱：**可选、延后**（源文档称"重要实体可再加简单图谱"）`[Q]`(Q13)。

### 4.2 hybrid 召回机制

- **机制**：入库时**切块 + 嵌入**；查询走 **hybrid = BM25（精确词/标识符）+ 向量（语义/换述）**，可加 **RRF 融合**、需要时再加轻量 **Rerank**。
- **为什么混合**：单一检索引擎覆盖不了真实查询分布——精确标识符（函数名、报错码、专有名词）靠 BM25 更准，自然语言/同义表述靠向量更准，融合后互补。
- **可行性**：`[A]` 机制可行（本地 FTS5 + 本地嵌入如 Ollama，不需联网、不需托管，符合"本地可控"）。
- **效果（v1.4 更新，T27）**：`[实测]` **对照基线已建立**——BM25-only（Logseq-only 428 条、26 条 query、**文件级主口径**）：**recall@1 0.6154 / recall@3 0.7692 / recall@5 0.8462 / recall@10 0.8462、MRR 0.7003**。**"强于关键字"仍未获证明**：M3（同义/词形扩展）**未超过**基线（多组更差、最好仅 @1 打平）；**M2（向量 hybrid，T27 已真跑）也未超过**——线上 embedding（`text-embedding-3-large` 3072 维 / RRF `k=60`）下 **recall@1 0.5000 / recall@3 0.7692 / recall@5 0.7692 / recall@10 0.8077、MRR 0.6324**，主口径**全面落后**。→ 全文一律表述为"**目标 + 已建立对照基线（未优于关键字）**"，**严禁写成"已实现更强召回"**（`09-recall-baseline-report.md` §6；M2 状态 `[Q]`→`[实测]`，**限"单次运行 / 未做参数择优 / 26 条样本"范围**，不宜过度解读）。 **v1.5（T31/T33/T34）**：改用**本地 embedding**（`BAAI/bge-base-zh-v1.5` / `jina-embeddings-v2-base-zh`，均 768 维、局域网 `$EMBED_ENDPOINT`、**无 key、零外发**）重跑，并做**预注册对照**（加权 RRF 3:1/2:1/1:1、表面路由、召回并集、标题 token ×4、标题×4×路由叠加）——**没有任何配置使 hybrid 强于词法基准**：加权 RRF 与并集因**稀释中文首位命中**而落后（A 3:1-jina @1 仅 0.5000）；表面路由仅 jina 非劣（@5 0.8846▲ / @10 0.9231▲ / MRR 0.7144▲、@1/@3 持平）而 bge 打平；**标题×4 提升的是 BM25 本身**（@1 0.6923▲ / @10 0.8846▲ / MRR 0.7474▲）；D1×B 叠加（jina @1 0.6923 / @10 0.9615 / MRR 0.7615）**在公平基准 D1-BM25×4 上仍未强于**（bge 逐条打平），增益主体来自标题×4（`09-recall-baseline-report.md` §6.6/§6.7/§6.8）。

- **可验证前提（否则不可验证）**：建 **20–30 条评测集** + 定指标（Top-1 ≥ 70% / Top-5 ≥ 90% `[A]`）+ **同时测纯关键字基线做对照** + 定义"无结果"口径。`[实测]`（v1.3）评测集 **26 条**已建、BM25 基线已跑（阈值仍需用户校准，标 `[A]`）。
- **实施先后顺序（v1.2 澄清，R2）**：**先连通 Logseq 与为知（Markdown）数据**（先有真实语料库）→ **再由 AI 辅助用户共建评测语料（query set）** → 最后跑对照评测。**数据连通先于评测语料建设，顺序不得颠倒。**
- **进展（v1.4）**：步骤①**部分完成**——Logseq 428 条已连通、**为知跳过**（T21）；步骤②**完成**——query set 26 条已建并经用户确认；步骤③**基线已跑（BM25-only）**；**M2（向量 hybrid）已于 T27 用线上 embedding 真跑并回填**——**未强于 BM25-only**，**仅救回跨语言盲区**（详见本节"效果/结构性发现"；报告 `09-recall-baseline-report.md` §6）。 **v1.5（T31/T33/T34）**：步骤③进一步做**改进对照**——加权 RRF / 并集 / 表面路由 / 标题×4 / 标题×4×路由叠加**均未使 hybrid 强于词法基准**；唯一稳定净增益为**标题×4（词法侧）**。建议（未获批、未验证）**BM25（标题×4）为主 + 向量仅作跨语言兜底**，或换**更强跨语言语义源**后重测。

### 4.3 召回呈现规范（结果卡）

- 对话是**唯一检索入口**（不做搜索框）。
- 每条结果**必须带来源路径 + 行号**（可核查、建立信任）；相关度用**弱化数字**（如"相关度 0.87"）而非进度条，避免过度暗示确定性。
- 命中数用徽标表达（如 `命中 N 条`）；**低置信候选**必须与"高相关命中"区分呈现。
- **无确认动作**：结果卡是**只读**的（读放开）。

### 4.4 "未找到"是一等状态（E-01）

- 召回无结果时**如实返回"未找到"，不得由 AI 编造答案**（对齐 T3 E-01、E-02）。
- 空态给出口：「换个说法再试 · 确认该内容是否已导入 · 查看已导入范围」。
- 视觉上明确、不可被 AI 文字糊弄过去（`未找到` 徽标 + secondary 边色）。
- 需在召回评测中**回归**（无结果用例 100% 如实"未找到"）。

## 5. 安全 / 密钥层（诉求④·安全半边）

### 5.1 目标与可核验判据

- **唯一判据**：`知识库文件 + 向量索引 + 运行日志 + 导出物` 中**明文 secret 命中数 = 0**。 `[A]`
- **五个环节同时零明文，缺一即破功**（`05` §4.1 升级结论）：
  1. **导入解析前**：历史笔记很可能**本来就写着密码** `[A]`(A5) → 导入管线必须先做 **secret 扫描/脱敏**，否则明文会进向量索引；
  2. **索引层**：向量库/全文索引**不得入库明文**，检索结果不得返回明文片段；
  3. **渲染层**：UI/日志/会话记录**永不出现明文**（= P3 永不呈现）；
  4. **AI 上下文层**：secret 不进 LLM 上下文（或仅以占位符/引用出现）；
  5. **导出/迁移层**：带走的只是**引用关系**，不带任何凭据。

### 5.2 只存指针的模型

- 知识库条目 = **账号引用（Account Ref）**：账号名 + 用途 + 存放位置 + `vault:` 指针（如 `{{secret:vault:github/pat#1}}`，等宽）。
- **凭据本体**由本机 **Bitwarden**（v1.1 决策锁定）持有；系统只调"取用/填充"接口。 `[选型依据]` 源文档"密钥层"与"回答 1 · 安全"：Agent 只调填充/取用接口，正文不存明文。
- **不自研密钥库**（N4）。

### 5.3 密钥四态呈现模型（P0–P3）

| 呈现态 | 触发条件 | 界面上出现什么 | 是否出现明文 |
|--------|----------|----------------|--------------|
| **P0 不存在** | 该账号无引用 | 无渲染；或"管理工具中暂无此凭据" | 否 |
| **P1 存在但不可见（默认）** | 存在账号引用 | `🔒 账号引用 · vault:<provider>/<item>#<name>` + 存放位置 + 用途 | **否（零字符）** |
| **P2 掩码可见（受限）** | 用户显式"短暂显示"且保险库已解锁 | 首尾各留少量字符，**5s 后自动复原** | 否（仅掩码） |
| **P3 完整明文** | —— | **本系统 UI 永不呈现**；反填时由密码管理器直接写入目标字段 | 否 |

### 5.4 呈现硬规则（可执行）

1. **默认最严**：任何未显式请求的状态都是 **P1**，界面不含 secret 任何字符。
2. **颜色即类型**：密钥相关内容一律 `vault/secret` 紫 + 🔒，与普通知识视觉隔离。
3. **复制即引用**：`[复制]` 复制 **token**，不复制明文。
4. **不落日志、不入上下文**：UI 层不缓存、不写日志、不送进对话；P2 明文 5s 自动复原。
5. **失败也脱敏**：填充失败只报 `provider/item#n` 与错误码，不回显任何 secret 片段。
6. **降级不可回退到明文**：保险库未解锁时只能引导用户去解锁，**不得**在知识系统内展示明文。
- **⚠ 呈现层验证空缺（v1.1 用户决策）**：密钥脱敏呈现的 **P1（零字符）/ P2（掩码·受限·短暂显示后复原）** 两态属**UI 呈现层**，其真实渲染验证**推迟至实现阶段补验**；当前**留空缺、明确标"待实现阶段补验"，不得视为已验证**（§9.1 R3、附录 A.6/A.7）。
- **明确禁止的反例**：附"点击显示明文"；把 secret 写进会话消息/URL 参数/localStorage；用"前 3 位"当安全展示；导入预览里**原样回显**笔记中的明文 secret。

### 5.5 疑似密钥混入写入的拦截（E-15）

- 写入确认卡在落库前做**密钥明文扫描提示**；若检出疑似 secret → 卡片升级为 `semantic/danger` 并**阻止直接写入**，转为"转密钥工具 / 脱敏引用"出口。
- 导入预览中若含明文 secret → **就地替换为引用 token**，并在"丢失/脱敏清单"标注（不得原样回显）。

## 6. 反填机制（诉求④·可用半边）

### 6.1 表述纪律（硬要求）

> 本方案对反填**只承诺**："**指针化 + 运行时取用 + 脱敏**"。
> **禁止**出现"一键反填到任意表单已实现"或等义表述；通用跨表单/跨应用自动填充列为**不做**（N9）。
> **主用途（v1.2 澄清，Q4）**：反填的主用途锁定为「**供 AI agents 使用**」——agent 在运行时**按引用取用凭据**；**其他场景（人手工反填到表单/浏览器等）暂不考虑，但保留可能性**。

### 6.2 机制

- **指针化**：知识库只存引用，不存值。
- **运行时取用**：需要时才由密码管理器取出——**Bitwarden（v1.1 锁定）**，以 **Bitwarden CLI / 浏览器扩展**为主取用通道；1Password CLI（`op read` / `op run`（默认脱敏）/ `op inject`）仅作**备选**。`[Q]` Bitwarden 的具体子命令与"免手工复制"的自动化填充能力**以实现阶段官方文档为准，本方案不臆造**。
- **脱敏**：明文不落知识库/日志/AI 上下文。
- **取用主体与触发（v1.2）**：**主用途 = 供 AI agents 运行时取用**——agent 侧只出现**引用（Account Ref）**，实际取用由本地受信通道执行；**明文不经 AI 上下文、不落知识库/日志、不呈现**。agent 的取用请求**不构成对明文的自主获取**（无人工/受信通道介入则不返回明文）；人手工反填路径暂不实现（N9 保留 agent 扩展可能性）。

### 6.3 落点与可行性现状

**主用途（v1.2 澄清，Q4）**：「**供 AI agents 使用**」——agent 运行时按引用取用凭据；人手工反填（浏览器表单 / 终端 / 桌面 App）**暂不考虑，但保留可能性**。

| 落点 | 现状（v1.2 口径） |
|------|------|
| **agent 运行时取用（主用途）** | agent 侧仅持**引用**、明文经受信通道取出；**端到端未验证** `[Q]` |
| 浏览器表单（人手工） | 需浏览器扩展/连接器；**暂不做**（保留可能性） |
| 终端 / CLI（人手工） | 可用 CLI 注入环境变量；**暂不做**（保留可能性） |
| 桌面 App（人手工） | 需辅助功能 API，**未验证**；**暂不做**（保留可能性） |

- **结论**：`[A]` 隔离（零明文）机制可行；`[Q]` **反填（agent 取用）端到端仍未验证**。首版**只做 agent 运行时取用这一条**，人手工反填不做（N9），避免过度设计。

### 6.4 关键安全点：不经 AI 上下文

- 反填**不得经过 AI 上下文**：即便主用途是"供 agent 取用"，**agent 侧也只接触引用**；实际取用由本地受信通道（companion / 密码管理器）执行，**只向 agent 返回"已取用/失败"结果**，不把明文回给模型。
- 此机制**设计上成立、行为未实测**（v1.2：agent 取用路径端到端待验，R4）。

### 6.5 界面要点（反填浮层 V3）

- 默认态**零明文、零字符**：普通引用条目连掩码都不给，只给"存在 + 存放位置 + 用途"。
- 触发后视觉明示"**由密码管理器执行，系统未接触明文；本页不显示、不缓存、不记录**"。
- 受限"短暂显示"降级路径（P2）是否保留 MVP `[A]`/`[Q]`（Q11）待确认；即便保留也先掩码、定时复原、不落日志。

## 7. AI 会话交互与写入边界（诉求①⑤⑥）

### 7.1 核心原则：读放开 · 写收紧

- **读放开**：召回顺滑、无需确认、只读呈现。
- **写收紧**：任何写入（新增/修改/删除）必须经用户**显式确认**；可撤销、可审计。
- **语义基础**：AI 的写入意图是**提案（Proposal）**，**≠ 动作（Action）**；未确认前不产生任何落盘。

### 7.2 最小 UI 视图清单（无导航体系）

| 视图 | 名称 | 作用 |
|------|------|------|
| V0 | 会话主视图（**常驻**） | 对话召回 + 会话录入的唯一主入口 |
| V1 | 写入确认面板 | 提案 diff + 确认/编辑/放弃 |
| V2 | 召回结果 | 来源、片段、相关度、展开 |
| V3 | 密钥引用 / **反填浮层** | 账号引用条目 + 反填触发 + 脱敏态 |
| V4 | 审计与撤销 | 写入历史、撤销入口 |
| V5 | 导入向导 | 来源选择 / 保真度 / 确认落库 |
| V6 | 设置 | 连接器状态、MCP 接线 |

- **无导航体系**；不做 Notion 式管理页（N1）。侧栏只承载"待确认队列 / 审计与撤销入口 / 连接器状态"这类**状态可见性**短区。
- 视觉复杂度预算压在**卡片状态机**与**脱敏表达**上，而非页面数量——页面越少越好。

### 7.3 状态语言（边色 + 徽标，贯穿全站）

| 状态 | 左边条色 | 徽标 | 关联界面 |
|------|----------|------|----------|
| 待确认（写入） | `semantic/warning` | `待确认` | V1 |
| 已确认 | `semantic/success` | `已确认 · 可撤销` | V1 完成态 / 状态条 |
| **已确认 · 撤销已过期** `[裁决补充]` | `text/secondary` | `已确认 · 撤销已过期` | V4（对应 E-14） |
| 已撤销 | `text/secondary` | `已撤销` | V4 |
| 命中（召回） | `accent/primary` | `命中 N 条` | V2 |
| **低置信 · 候选** `[裁决补充]` | `semantic/warning` | `低置信 · 候选` | V2（对应 E-02） |
| 未找到 | `text/secondary` | `未找到`（**无伪造内容**） | V2 空态 |
| 账号引用（密钥） | `vault/secret` | `🔒 账号引用` | V3 / 正文 |
| 保真度告警 | `semantic/warning` | `保真度 X% · 丢失 N 项` | V5 |

- 语义色**永不单独承载信息**：一律"**颜色 + 图标 + 文字标签**"三件套（色盲安全）。
- **三项状态可见性**（贯穿原则，规格在此定稿）：① 召回可用性 `🟢/🟡/🔴`；② 密钥工具连接状态；③ 索引状态。三者统一复用 `success/warning/danger` + 文字标签。
- > `[裁决]` 本表已合入 `05` §6 的命名统一与状态补齐：**知识库侧统一用「账号引用」**（"凭据"一词保留给外部 Secret Entry）；补 **低置信·候选**、**撤销已过期** 两态与三项状态点规格。

### 7.4 确认闸门（诉求⑥核心）

**唯一拦截点**：位于**知识 MCP 写接口之前**——不是 UI 问题，是**协议层问题**。

**⚠ 重要缺口（`05` §5.3，动工前必须定稿）**：若知识 MCP 暴露**无条件的 `add`/`update`**，AI 客户端（Cursor/Claude）可直接调用、**跳过**确认面板 → "100% 经确认"不再成立。**仅靠提示词不足**。

**强制机制：知识 MCP 不暴露直接写，改两阶段协议**：
1. `propose_write(...)` → 返回 `proposal_id` + diff（**不落盘**）；
2. `commit_write(proposal_id, confirmation_token)` → 仅当 token 由**用户确认动作**签发时才执行写入；
3. **AI 侧拿不到 `confirmation_token`**，因此无法自行提交；
4. 宿主客户端的**工具调用审批钩子**可作第二道保险，但**不单独依赖**。
- **等级**：`[实测]` 机制在**最小 MCP 服务端实现**中已验证（`07-mcp-spike-report.md` §5.1：22/22 断言通过；`missing_token`/`bad_signature`/`token_expired`/`token_replayed`/`baseline_changed`/`proposal_expired` 各类拒绝路径全部正确触发，**拒绝时目标文件零改动**）。**宿主客户端侧的确认入口仍为 `[Q]`**（**目标客户端：Cursor / deepseek harness**；是否内联渲染、是否有审批钩子须真实客户端实测，见 §9.2 Q16/R11）。
- **口径**：在**最小服务端实现范围**内，"100% 写入可确认"由"设计目标"升级为"**已定强制机制 + 机制已实测成立**"（**前提**：知识 MCP 不暴露裸 `add`/`update`/`delete`）；但**不得外推为生产实现已就绪**——token 重放表 / job 状态的跨进程可见性、写入原子性仍未验证（§9.1 R12）。
- **宿主侧证据（v1.3，T22）**：`[实测]` 本 harness（deepseek harness）**连接器由宿主 SQLite 统一管理**（`mcp_connectors` 30 行，schema 原生含 `command/args_json/env_json` → 支持 stdio，stdio 实体 2 条）；宿主另有**授权/审批记录子系统**（`authorization_approval_records`，列含 `decision/scope/approval_source/matched_rule_id/decided_by`，本轮 **0 行**未触发）。这**印证"审批 / 授权是宿主职责、非 MCP 原语"**；但**审批是否作用于 MCP 工具调用、如何向用户呈现仍 `[Q]`**；且 **agent 无连接器注册工具 → 挂载本地 server 须宿主侧动作**（`10-host-support-report.md` §7）。
- **同类风险**：`logseq-mcp` 等**第三方写工具同样必须纳入该协议**（§3.2 约束②）。

**确认分级决策表**：

| 操作 | 是否需确认 | 说明 |
|------|-----------|------|
| `search`（读） | **免确认** | 读放开 |
| `add` / `update`（写） | **必确认** | 走两阶段协议 |
| `delete`（删） | **必确认 + 二次确认** | 破坏性最高 |

**知情同意四要素**（确认卡必须表达）：**改什么 / 改哪 / 怎么来的 / 能不能反悔**。

### 7.5 可撤销与审计

- 写入后转"**已确认 · 可撤销**"并显示**来源会话 + 时间**（审计可见性）。
- 撤销窗口 `[A]`/`[Q]`（默认 1 会话 / 24h，Q5+§未决 R8）未定稿；窗口过期后转"撤销已过期"态（E-14）。
- 审计记录：来源=哪次会话、时间、结果（成功/失败）——**不含任何 secret 明文**。

### 7.6 会话录入与"建议落库"

- 会话中抽取"值得记的部分"并**建议落库**；**建议落库同样算写入、同样走确认**（`[Q]` Q14，默认策略：算写入）。
- 召回无结果时如实说"未找到"（§4.4）。

## 8. MVP 与里程碑

### 8.1 MVP 最小起步集（M1–M7）

**目标**：先跑通"**本地库 → 知识 MCP → 会话召回 → 会话录入（确认后落库）**"的可用闭环，并把密钥**隔离**到位。
`[选型依据]` 源文档"起步最小集"仅三项（笔记目录 / 知识 MCP / Bitwarden·1Password）；本方案在基础上补齐**写入确认闸门**（硬约束）与**最小导入通路**。（**v1.1**：密码管理器**锁定 Bitwarden**，1Password 不作目标。）

| # | MVP 组件 | 说明 | 优先级 |
|---|----------|------|--------|
| M1 | 一个本地笔记目录（Markdown 真相源） | 唯一真相源，可迁移、可外部编辑 | P0 |
| M2 | 一个知识 MCP（hybrid 召回 + 两阶段写接口） | 切块+嵌入、BM25+向量混合检索 | P0 |
| M3 | 密码管理器（**Bitwarden**，v1.1 锁定）+ 指针化取用接口 | 知识库零明文、只存指针 | P0 |
| M4 | 读写通道：`search`（读放开）/ `propose_write`·`commit_write`（写需确认） | 落实"读放开、写收紧" | P0 |
| M5 | 写入确认闸门（含撤销） | 诉求⑥落地 | P0 |
| M6 | 最小导入通路（≥1 条，**Markdown 系**：Logseq（**已连通**）/ 通用带附件 Markdown 目录 → Notion） | 证明导入可行；为知**跳过**（v1.3） | P0(首批) |
| M7 | 反填基础能力（**指针化 + 运行时取用 + 脱敏**，单场景） | 需求④可用半边；**不承诺"一键反填到任意表单"** | P1 |

### 8.2 MVP 完成定义（DoD）

用户能在一个 AI 助手里，用自然语言问出以前记过的知识（**语义、非关键字**）；能把一段对话内容**经确认后**写入本地库；且**知识库与导出物中扫描不到任何明文密钥、仅存指向密钥的指针**。

### 8.3 分批交付与里程碑

| 阶段 | 内容 | 前置 |
|------|------|------|
| **M-a 闭环** | M1+M2+M4+M5：本地库 + 知识 MCP（含**两阶段写协议**）+ 确认闸门 | 两阶段协议定稿（R1） |
| **M-b 密钥隔离** | M3：密码管理器指针化取用 + 零明文扫描 | — |
| **M-c 最小导入** | M6：先打通 Markdown 系（Logseq → Notion） | 导入保真度口径（§3.4） |
| **M-d 反填可行性** | M7：单场景（默认浏览器）指针化取用验证 | 反填落点确认（Q4） |
| **M-e 为知导入** | **v1.3：跳过**（T17 导出物仅目录骨架、无内容文件）；能力并入通用"带附件 Markdown 目录"通路 | —（已由 T21 收口） |

> 分批原则：**先打通 Markdown 系通路（Logseq 已连通 → 通用带附件 Markdown 目录）**；**MVP 不追求召回量化达标**（那属评测里程碑，见附录 A §1）。

### 8.4 优先级口径（全文统一）

**P0** = 阻塞性或核心必备；**P1** = 影响体验、可后置；P2 = 可延后。
**能力域汇总**：L2、L5 = P0 核心；L3 = P0 安全基石；L1 = P0 但分批；L4、L6 = P1。

## 10. 落地形态与实现机制（开放讨论结论并入）

> 本章为开放议题（**落地形态** + **确认闸 / 进度条的真实实现机制**）讨论结论的正式并入，是 §2 架构的落地补充与 §7.4 机制的展开。**冲突处以 §7 为准**；术语与口径全文统一（两阶段协议：**机制已在最小 MCP 服务端实现中实测通过，宿主侧待验**，见 §7.4 / §10.3）。

### 10.1 三层形态（通用优先）
- **数据层 = 本地 Markdown / 纯文件夹**：100% 通用、宿主零耦合；换助手不迁数据，索引（FTS5 + 本地向量）可重建（对齐 §4.1、诉求①"本地可控"）。
- **访问层 = 本地 MCP Server**：对外工具 **`search` / `propose_write` / `commit_write`**（+ 密钥连接器）；工具签名即契约，可被 Cursor / Claude / 其它 MCP 宿主复用，**不绑单宿主**（诉求①"自己接 MCP"）。
- **呈现层 = 可选最小 local companion**（确认页 / CLI / 托盘）：仅在宿主不提供能力时兜底（§10.3"授权不外包"）。
- **不做**：独立 App（桌面/移动，Electron/Tauri 等）——绑定入口、与"弃用界面化工具"冲突（**N10**）；**寄生单宿主的"纯技能"**——只作**薄分发封装**，不承载能力本体。

### 10.2 通用性排序与必然耦合边界
- **可全通用（跨宿主 100%）**：数据格式 / 数据契约、检索接口、写入协议（两阶段）、导入管线、job 状态机。
- **排序：数据契约 > MCP 工具签名 > UI**。
- **必然耦合宿主（不可能通用）**：① **确认面板怎么弹**；② **反填落点**（浏览器 / 终端 / App）；③ **上下文注入**（提示词 / 工具暴露方式）。
- **代价**：a) 用户需多跑一个本地组件；b) **多宿主并发**下 stdio MCP 会被各客户端各起实例、并发读写同一状态 → 需**单例 daemon 或至少单写者**（WAL + 文件锁）。`[实测]` 由建议级升为**必需项**：8 进程 × 50 次自增**直写丢 363/400（≈91%）**，**单例 daemon 单写者丢 0**（`07-mcp-spike-report.md` §5.2）；生产级跨进程状态与原子写仍未验证（§9.1 R12）。

### 10.3 确认闸的两阶段实现（机制已实测 · 宿主侧待验）
> 口径校正：本节机制已由 T10 Spike 在**最小 MCP 服务端实现**中实测通过（`07-mcp-spike-report.md` §5.1 / §6-1~4），**限于该最小实现范围**；宿主客户端侧（确认入口是否内联、是否有审批钩子）仍为 `[Q]`。
- `propose_write(payload)` → 返回 `{proposal_id, diff, ttl}`；**不落盘**，入本地 `.pending` 队列（崩溃可恢复）。`[实测]` propose 后目标文件 `exists=false`。
- 用户经**本地受信通道**确认 → 签发**一次性** `confirmation_token`：绑 `proposal_id` + 目标路径 + **基线内容 hash**（防 TOCTOU，对齐 E-09）；**AI 不可获得 token**（E-17 落点）。
- `commit_write(proposal_id, token, …)` 校验通过后落盘；**无有效 token 一律拒绝、写入不发生**。`[实测]` 校验顺序：token 存在 → 签名（`timingSafeEqual`）→ `proposal_id` 匹配 → `baseline_hash` 匹配 → token TTL → 一次性未重放 → **提交前重算目标文件 hash 与基线比对**（不符返回 `conflict`，不覆盖）。
- **两个独立 TTL**：`proposal_ttl`（待确认过期 → 提案作废、不落盘，**E-18**）≠ `undo_window`（commit 后撤销窗口，过期转"已确认·撤销已过期"，**E-14**）；另有 `token_ttl`（token 有效期）。`[实测]` 三者语义可分且独立生效（`proposal_expired` ≠ `token_expired`）。**默认值区间（可配置）**：`proposal_ttl` 60s / `token_ttl` 30s / `undo_window` 60s `[A]`（待定稿，Q5）。
- **写入状态机**（本地持久化，SQLite）：`draft → proposed → awaiting_confirm → committed / rejected / expired`；**协议拒绝码**（实测，供确认卡文案 1:1 映射）：`missing_token` / `bad_signature` / `token_expired` / `token_replayed` / `proposal_expired` / `conflict(baseline_changed)`。
- **原则**：**授权动作与面板渲染解耦——UI 可嵌入、授权不可外包**；知识 MCP **不得暴露裸 `add/update/delete`**，第三方 `logseq-mcp` 写工具同受此约束（对齐 E-17）。

### 10.4 导入 / 写入进度：本地 job 状态机（机制已实测 · 宿主渲染待验）
- **事实源 = 本地 job 状态机**：`job_id / phase / done / total / errors[]`；MCP 暴露 **`get_job_status` / `cancel_job`**。`[实测]` `start_import` 立即返回 `job_id`，`get_job_status` 可查终态（`done`/`cancelled`）。
- MCP `notifications/progress`（`progressToken`）**仅作可选渲染通道、非保证**——须能力协商，宿主支持才内联渲染，否则降级为**完成时一次性报告 + 丢失清单**（对齐 E-11/E-12）。`[实测]` 服务端**可主动发出**该通知且被 stdio 对端收到（8 条、单调 1→8、含 message）；**宿主客户端是否转发/渲染仍为 `[Q]`**（**目标客户端：Cursor / deepseek harness**，v1.2；§9.2）。
- **宿主侧证据（v1.3，T22）**：`[实测]` 本 harness **连接器由宿主 SQLite 统一管理**（`mcp_connectors` 30 行，schema 含 `command/args_json/env_json`）、**原生支持 stdio**（stdio 实体 2 条）→ 具备挂载本地 stdio MCP server 的能力；宿主另有**授权/审批记录子系统**（`authorization_approval_records`，本轮 0 行）。**agent 无连接器注册工具、无用户可写连接器配置 → 挂载须宿主侧动作**（`10-host-support-report.md` §7）；**渲染与审批行为仍 `[Q]`**。
- **取消语义**：`[实测]` `cancel_job` 后**暂存丢弃、无部分写入**（无 staging 残留、无最终文件）——与 E-11/E-12"部分导入不落地"一致。
- **UI 只是投影，事实源在本地 job**；分条幂等 + 重试保证逐条可见。

### 10.5 规范依据与动工前 spike
