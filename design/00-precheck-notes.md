# 前置预研笔记：三来源导入 / 召回 / 密钥反填 可行性

> **性质声明**：本文件是 **初步、待验证** 的外部事实核验笔记，**不是最终结论**，也不代表能力已实现。
> 用途：作为 T2（能力架构）、T3（导入与写入流程）作者的共享前置输入，避免前序方案引用未经核验的能力。
> 覆盖范围：T5 核验项 1)–3)（不依赖 T3/T4 的部分）。第 4) 项（AI 会话写入的用户确认边界）留待 T3 完成后结合核验。
> 核验方法：桌面检索 + 官方/社区公开资料比对（截至 2026-10-17）。**未做实际安装与端到端跑通**，所有结论均标注证据强弱。

---

## 核验项 1：三来源导入（Notion / Logseq(mcp-logseq) / 为知笔记）

**结论（初步）**：三者均"可导入"，但自动化程度与成本差异很大，**不应在任何方案里被描述为同等成本的一步到位**。建议在能力架构中显式分三层：Notion、Logseq 属"较低成本"，为知笔记属"最高成本、需独立适配层"。

### 1.1 Notion

| 维度 | 内容 |
|------|------|
| 结论 | 可行，且路径最多；推荐**只读导入** |
| 证据 | 官方支持页面/数据库导出 Markdown + CSV；官方 API 支持逐块拉取（`GET /v1/blocks/{id}/children`，递归取子块）；社区已有 Notion MCP Server（如 suekou/notion-mcp-server） |
| 关键限制 | 该 MCP 的 Markdown 转换被标注为**实验性**：查看内容可显著省 token，但**编辑场景会丢失原始结构** → 仅建议用于读取/导入，写入不应依赖它 |
| 待验证 | 导出后图片/附件路径、数据库关系、嵌套子页面在本地重建的完整度；大工作空间的分页与限流 |

### 1.2 Logseq（mcp-logseq）

| 维度 | 内容 |
|------|------|
| 结论 | 可行，**现成 MCP 已存在**，是三来源里最顺的一条 |
| 证据 | 社区 logseq-mcp（走本地 Logseq API + `LOGSEQ_API_TOKEN` / `LOGSEQ_API_URL`），工具集含：列 graph、列页面、取单页内容、跨页 search、create/update/delete page |
| 关键限制 | 需配置本地 API 与 token；对网络环境有一定依赖；"删除/更新页面"属写操作，接入时需纳入写入确认边界（见第 4 项） |
| 待验证 | 块级结构、双链/引用、属性（properties）在导出为通用 Markdown 时的保真度 |

### 1.3 为知笔记（WizNote）

| 维度 | 内容 |
|------|------|
| 结论 | **无官方 MCP，必须自建导出/适配层**，是三来源中成本最高者 |
| 证据 | 社区方案（如 ExportToMd 插件、直接解析本地库的脚本）已存在，但均为第三方、非官方、稳定性自担 |
| 关键限制（已暴露） | ① 完整/批量导出受**会员权益**限制（普通/子账号部分导出项不可用）；② 底层以 HTML 存储，导出正文带**内联样式残留**，直接转 Markdown 排版易乱；③ 图片走 **`wiz://` 内部协议**，需重映射为本地路径；④ **加密笔记**需先解密；⑤ **协作笔记**走 WebSocket 通信，需自定义解析器（且要求客户端别打开该笔记，否则读取受影响） |
| 待验证 | 各笔记类型（HTML / Lite(markdown) / 协作）的实际解析成功率；加密笔记批量解密的可行性与安全影响 |

**给小结论来源的直接影响（供 T2/T3 参考）**：
- T2 能力架构中，导入层应把"为知"单列为**需独立适配、成本/风险最高**的一项，并明确"首版是否覆盖全类型"。
- T3 导入流程中，为知导入应具备**人工可介入的降级路径**（如导出失败 → 半自动/手动目录导入），而不是假设一次成功。

## 核验项 2：召回强于关键字匹配（全文 + 语义混合检索）

| 维度 | 内容 |
|------|------|
| 结论（初步） | **可行**。BM25 + 向量混合检索（可加 RRF 融合 / Rerank 重排）是当前本地 RAG 的主流成熟路径，**在机制上确能强于纯关键字匹配** |
| 证据 | 存在成型的本地混合检索实现：① 纯本地代码库 RAG MCP（BM25 + 语义向量，全链路本地、零 API 费）；② SQLite FTS5 + BM25 + 自建向量的 MCP 全栈实践；③ 本地嵌入可由 Ollama / 本地 GGUF 模型提供 |
| 机制解释 | 单一检索引擎覆盖不了真实查询分布：**精确标识符**（函数名、报错码、专有名词）靠 BM25 更准，**自然语言/同义表述**靠向量更准；两者融合后互补 |
| 关键限制 | ① 效果上限取决于**本地嵌入模型**（弱于云端旗舰模型）；② 大规模库的索引耗时/检索延迟受本机硬件约束；③ 分块（chunk）策略显著影响召回质量 |
| 待验证 | "强于关键字"目前是**机制层面**的推断，**未有本项目的量化对比**（需要评测集与指标，见后续验证清单） |

## 核验项 3：密钥隔离与快速反填（知识库不落明文）

| 维度 | 内容 |
|------|------|
| 结论（初步） | **"知识库只存指针、运行时取用、输出脱敏"可行**；但**"一键快速反填到浏览器/表单"的端到端路径仍属待验证项**，不可宣称已实现 |
| 证据 | ① 1Password CLI（`op read op://...`、`op item get --field`；`op run` 运行时注入并**默认脱敏**；`op inject` 模板注入不落明文）；② Bitwarden CLI 与浏览器扩展/系统自动填充能力成熟 |
| 可行的分离模型 | 知识库仅存"哪有账号、用在哪、怎么用"（指针/描述），**绝不存 secret 本体**；需要登录时经密码管理器接口取用 |
| 关键限制 / 待验证 | ① "反填"落到**任意应用/表单**的自动化程度不一致：浏览器场景较成熟，桌面/自定义表单需额外适配；② 密码管理器 CLI 的会话解锁（`op signin` / Bitwarden 解锁）与 AI Agent 的调用链如何衔接，尚无端到端验证；③ 需明确 secret **不进日志、不进模型上下文**的约束是否被链路遵守 |

## 核验项 4：AI 会话写入的用户确认边界

**状态：待 T3 完成后核验**（依赖 T3 的交互流程定义）。

初步方向（仅记录，不作结论）：写入边界需要在 **MCP 工具层**具备可判定状态（如 `create/update` 类工具显式区分"建议"与"提交"，提交前返回待确认对象给用户），而不是仅靠提示词约束。是否可以低成本实现，届时结合 T3 的确认闸设计一并核验。

## 未验证项与风险汇总

1. **全部结论均为资料级核验**，未在本项目环境实际安装/跑通任一 MCP 或导出工具 → 存在"文档可行、实际踩坑"的风险。
2. **为知笔记**：导出成功率、加密/协作笔记处理存在明确不确定性，是导入链最大风险点。
3. **召回"强于关键字"**：机制成立，但**缺量化证据**，属需实测的假设。
4. **反填端到端**：浏览器场景较有把握，非浏览器/任意表单场景未验证。
5. **写入确认边界**：能否在工具层（而非仅提示词层）可靠实现，待 T3 后核验。
6. **安全边界未检查**：secret 是否会经日志/上下文泄漏，尚无链路级验证。

## 后续验证清单（可执行检查步骤，T5 最终版将复用）

- [ ] **导入-Notion**：用一个小工作空间导出 Markdown+CSV，记录图片/附件/嵌套子页面/数据库关系在本地重建的完整度；调用一次 MCP 只读检索确认可读。
- [ ] **导入-Logseq**：本地起 Logseq + logseq-mcp，验证 列页面 / search / 取单页内容 三项工具；检查块结构与双链在导出 Markdown 中的保真度。
- [ ] **导入-为知**：分别取 1 篇 HTML 笔记、1 篇 Lite(markdown)、1 篇协作笔记、1 篇加密笔记，跑通/记录导出结果；确认图片 `wiz://` 路径是否被正确重映射；记录失败类型与人工降级耗时。
- [ ] **召回对比**：构造 20–30 条查询的评测集（含精确标识符类 + 自然语言同义类），对同一批笔记分别用"纯关键字(BM25)"与"BM25+向量混合"跑，记录命中率/首位命中/延迟，形成量化对比。
- [ ] **密钥反填**：搭一条最小链路——知识库条目只存指针 → 经 `op read`/`bw get` 取用 → 在浏览器登录页完成填充；同时抓取 CLI/Agent 日志，确认 secret 未落明文。
- [ ] **写入确认**：在 MCP 工具层构造"待确认提交"对象，验证用户在确认前知识库不发生写入（含失败/中断回滚）。
- [ ] **安全链路**：抽一次完整会话，检查向量库、日志、模型上下文中是否出现 secret 明文。
